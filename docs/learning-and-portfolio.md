# 학습 및 포트폴리오 운영 기준

이 프로젝트는 Debate Timer의 지표 자동 리포트 시스템을 구현하는 동시에, 백엔드 아키텍처·데이터 모델링·운영 설계·테스트 전략을 학습하고 이력서/포트폴리오에 활용할 수 있는 산출물을 남기는 것을 목표로 한다.

## 기본 원칙

- 단순히 가장 빠른 구현보다, 나중에 설명 가능한 구현을 우선한다.
- 면접에서 설명하기 쉬운 구현을 선호한다. 책임 경계가 명확하고, 트레이드오프가 드러나며, 테스트 가능한 동작과 운영상 가정이 문서화된 구현을 우선한다.
- 중요한 설계 결정은 문제, 제약 조건, 대안, 선택 이유, 검증 방법이 드러나도록 기록한다. 그 결정이 이후 작업에 영향을 준다면 관련 `docs/`, `specs/`, ADR 또는 체크리스트 파일에 판단 근거를 남긴다.
- 가장 짧은 구현만을 목표로 최적화하지 않는다. 사용자가 무엇을 만들었고, 왜 그렇게 만들었으며, 어떤 대안을 검토했는지 설명할 수 있도록 충분한 구조, 테스트, 문서를 유지한다.
- 보일러플레이트, 반복 작업, 단순 설정은 에이전트가 직접 처리해도 된다.
- 아키텍처, 데이터 모델링, 테스트 전략, 에러 처리, 운영 준비도처럼 면접과 실무 설명 가치가 큰 지점은 사용자가 이해할 수 있도록 짚고 넘어간다.
- 일반적인 문법 설명보다 이 코드베이스에서 왜 그렇게 설계했는지를 우선한다.

## 엔지니어링 스토리 기준

이력서나 포트폴리오에 활용할 수 있는 작업은 아래 흐름이 드러나도록 정리한다.

1. **문제**: 어떤 사용자 문제, 운영 문제, 제품 문제를 해결하려는가?
2. **제약 조건**: 무료 플랜, 데이터 보관 기간, API 한도, 개인정보, 시간, 현재 앱 구조 등 어떤 조건이 있었는가?
3. **의사결정**: 여러 선택지 중 무엇을 선택했고, 왜 그 선택이 현재 단계에 적합한가?
4. **구현**: 어떤 모듈, 데이터 모델, API, 스케줄러, 어댑터, 테스트를 만들었는가?
5. **검증**: 어떤 테스트, 수동 확인, 로그, 문서 검토로 동작을 확인했는가?
6. **남은 트레이드오프**: 지금은 미룬 것, 추후 확장할 것, 운영에서 다시 볼 위험은 무엇인가?

## 학습 참여 방식

학습 참여는 사용자가 직접 작성한 코드의 양보다, 중요한 판단을 직접 해보고 설명할 수 있는지를 기준으로 본다.

- 단순 문법, 보일러플레이트, 반복 작업은 에이전트가 직접 처리해도 된다.
- 의미 있는 학습 지점에서는 사용자에게 작고 명확한 기여를 요청한다.
- 요청할 수 있는 기여의 예시는 5-10줄의 코드, 테스트 케이스, 데이터 모델 판단, 에러 처리 정책, 또는 의도한 접근 방식에 대한 짧은 설명이다.
- 특히 설계 판단, 테스트 전략, 데이터 모델링, 실패 처리, 운영 제약은 사용자가 먼저 생각해볼 수 있도록 질문한다.
- 단, 초보자에게 막연히 "직접 해보라"고 요구하지 않는다. 사용자가 결정하거나 코드를 쓰기 전에 목표, 관련 제약, 가능한 선택지, 추천 방향, 검증 방법을 먼저 제공한다.
- 사용자의 기여 후에는 무엇이 맞고, 무엇이 위험하며, 어떤 점을 개선할지 직접 리뷰한다.

## 직접 코드 작성량 기준

직접 코드 작성은 많을수록 좋은 것이 아니라, 설명 가능한 핵심 조각을 직접 다루는 것을 목표로 한다.

- 사용자는 반복 구현자가 아니라 핵심 판단과 검증을 직접 해보는 주니어 백엔드 엔지니어 역할을 맡는다.
- 보일러플레이트, Nest 모듈 연결, 반복 설정, 단순 파일 이동은 에이전트가 대부분 처리해도 된다.
- 핵심 비즈니스 로직, 테스트, 데이터 모델, 외부 API 어댑터 경계, 에러 처리 정책은 사용자가 작은 단위로 참여하는 것을 우선한다.
- 한 작업에서 사용자의 직접 작성은 보통 5-20줄 정도면 충분하다. 단, 줄 수보다 테스트 가능성, 판단 근거, 설명 가능성을 더 중요하게 본다.
- 의미 있는 기능마다 최소 한 번은 사용자가 코드, 테스트, 데이터 모델, 또는 설계 결정에 직접 참여하도록 한다.
- 복잡한 기능에서는 많은 코드를 직접 쓰는 것보다 작은 테스트 1개, 스키마 일부, 핵심 함수 skeleton, 에러 처리 분기, 또는 query/data format 결정을 직접 해보는 것이 더 가치 있다.

예를 들어 Phase 1-1에서는 다음 작업이 좋은 학습 참여 지점이다.

- `ConfigModule` 환경변수 검증 테스트 케이스 작성
- Prisma 모델에서 `periodKey`, `querySpecVersion`이 왜 필요한지 설명
- `PrismaService`의 연결/해제 테스트 기대 동작 작성
- `timer_started` seed의 `querySpec` JSON 구조 제안
- `/health` 응답 계약을 테스트로 먼저 표현

## 학습 보조 방식

사용자에게 직접 판단이나 코드 작성을 요청할 때는 아래 정보를 먼저 제공한다.

1. **목표**: 지금 작성하거나 결정할 것이 전체 기능에서 어떤 역할을 하는가?
2. **맥락**: 관련 파일, 함수, 타입, 데이터 흐름은 무엇인가?
3. **제약 조건**: 이미 정해진 기술 선택, 테스트 기준, 운영 가정, 무료 플랜 한도는 무엇인가?
4. **선택지**: 가능한 접근이 여러 개라면 2-3개 선택지와 장단점을 제시한다.
5. **추천 방향**: 현재 단계에서 어떤 선택이 가장 적합한지 이유와 함께 제안한다.
6. **작성 범위**: 사용자가 작성할 코드나 설명의 크기를 작고 명확하게 제한한다.
7. **검증 방법**: 작성 후 어떤 테스트, 명령, 리뷰 기준으로 확인할지 알려준다.

사용자가 막히면 정답을 바로 넘기기보다, 힌트 → 부분 예시 → 전체 예시 순서로 지원한다. 다만 사용자가 빠른 진행을 요청하면 에이전트가 직접 구현하고 핵심 판단만 짧게 설명한다.

## 기록 위치

- 전역 설계와 장기 방향: `docs/implementation-plan.md`, `docs/tech-stack.md`
- 확정된 의사결정과 보류 항목: `docs/decisions.md`
- 큰 아키텍처 결정: `docs/adr/`
- 학습 아카이브: `docs/learning/`

- Codex 협업 방식과 Learning Mode: `AGENTS.md`

## 학습 아카이브 운영 방식

학습 아카이브는 모든 대화 내용을 자동 저장하는 공간이 아니다. 면접, 포트폴리오, 후속 구현에서 다시 설명할 가치가 있는 내용만 저장한다.

운영 흐름은 다음과 같다.

```text
후보 감지 -> 사용자 확인 -> 기존 노트 검색 -> 기존 노트 개선 또는 새 노트 생성
```

- 새로운 학습 후보가 나오면 먼저 짧게 알리고 저장 여부를 확인한다.
- 같은 주제나 겹치는 주제의 노트가 있으면 새 파일을 만들지 않고 기존 노트를 개선한다.
- 새 노트를 만들 때는 `docs/learning/{category}/YYYY-MM-DD-{topic}.md` 형식을 따른다.
- 구조, 데이터 흐름, 모듈 경계, 운영 흐름이 있는 주제는 ASCII 구조도를 포함한다.
- `docs/learning/README.md`는 새 노트를 만들 때만 인덱스를 갱신한다.

## Learning Mode에서 우선할 주제

Learning Mode에서는 다음 주제를 우선적으로 설명하고 확인한다.

- 모듈 경계와 의존성 방향
- 데이터 모델과 마이그레이션 설계
- 외부 API 어댑터와 실패 처리
- 멱등성, 재시도, 중복 방지
- 테스트 전략과 검증 기준
- 로그, 관측성, 운영 준비도
- 무료 플랜 한도와 데이터 보관 기간이 설계에 주는 영향

## 구현 중 학습 참여 기준

Learning Mode의 "진행" 승인은 구현 방향에 대한 승인이지 학습 참여 생략 승인이 아니다. 중요한 GREEN 구현 전에는 사용자가 직접 해볼 수 있는 작은 기여 지점을 만든다.

좋은 참여 단위는 다음처럼 작고 검증 가능해야 한다.

- 5-10줄의 핵심 함수 구현
- 실패하는 테스트 케이스 1개 작성
- 데이터 모델 필드나 저장 정책 선택
- 실패 처리 정책 문장 작성
- 구현 접근을 3-5문장으로 설명

예시는 다음과 같다.

```text
RED 확인
  -> GREEN 방향 설명
  -> 사용자 참여 지점 선택
  -> 사용자 기여 검토
  -> Codex가 통합 구현
  -> 테스트와 문서 정합성 검증
```

생략이 허용되는 경우는 boilerplate, 반복적인 파일 생성, 포맷팅, 이미 승인된 명세의 단순 전사처럼 학습 가치가 낮은 작업이다. 이 경우에도 왜 생략하는지 짧게 남긴다.

## 구현 후 문서 정합성 확인

구현 완료 전에는 코드 검증뿐 아니라 문서 정합성도 확인한다.

- `tasks.md`: 완료 여부, 검증 결과, 환경 blocker가 실제 상태와 맞는지 확인한다.
- `specs/feat/*`: 구현 중 결정된 제약이나 실패 처리 정책이 명세와 어긋나지 않는지 확인한다.
- `docs/learning/`: 재사용 가능한 학습 내용이 기존 노트에 반영됐는지 확인한다.
- `docs/learning/README.md`: 새 학습 노트를 만들었을 때만 인덱스를 갱신한다.
- `docs/README.md`: 새 문서 영역이나 중요한 문서가 추가됐을 때만 갱신한다.
- `AGENTS.md`: Codex 협업 방식 자체가 바뀌면 persistent instruction으로 갱신한다.

## 피해야 할 방식

- 문법 설명만 길게 하고 현재 설계 판단을 설명하지 않는 방식
- 동작은 하지만 나중에 설명하기 어려운 임시 구현
- 문서, 테스트, 검증 근거 없이 구현만 남기는 방식
- 모든 결정을 과도하게 일반화해 이 프로젝트의 실제 제약과 분리하는 방식
