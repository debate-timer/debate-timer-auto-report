# 지표 요약·분석·알림 자동화 기능 요구사항 명세서

## 1. 문서 개요

### 1.1 목적

본 문서는 제품 분석 도구에 수집된 지표를 주기적으로 조회하고, 이를 요약·비교·분석하여 팀 커뮤니케이션 채널로 전달하는 기능의 요구사항을 정의한다.  
본 기능의 목표는 단순한 수치 조회를 넘어서, **변화 감지 → 해석 보조 → 개선 액션 제안**까지 하나의 흐름으로 제공하는 것이다.
즉, 본 기능은 **지표/에러 데이터를 읽고, 제한된 도구를 사용해 원인 가설과 액션을 제시하는 AI 분석 시스템**을 목표로 한다.

### 1.2 배경

현재 제품 지표는 분석 도구에 수집되고 있으나, 팀원이 직접 대시보드에 접속해 수치를 확인해야 하며, 수치 변화가 실제 액션으로 연결되기까지 시간이 걸린다.  
이에 따라 핵심 지표를 자동으로 요약하고, 이전 기간과 비교하며, 이상 변화가 있을 경우 우선 확인할 항목과 개선 방향을 함께 전달하는 기능이 필요하다.

### 1.3 범위

본 명세서는 다음 범위를 다룬다.

- 분석 도구로부터 핵심 지표를 조회하는 기능
- 조회한 지표를 내부 형식으로 정리하는 기능
- 기간 비교 및 변화율 계산 기능
- 이상치 또는 주의 지표를 판별하는 기능
- 오류 모니터링 도구로부터 에러 정보를 조회·요약하는 기능
- 지표 변화와 에러 발생을 함께 해석하는 기능
- AI 기반 요약 및 개선안 생성 기능
- 팀 채널로 리포트 및 경고를 전송하는 기능
- 실행 결과 및 이력 저장 기능

본 명세서는 특정 기술스택, 프레임워크, 외부 API 구현 방식은 확정하지 않는다.

### 1.4 제약 및 전제

본 기능은 다음 제약 조건 하에 설계된다.

#### 1.4.1 데이터 원천 과도기

- **GA4**: 전역에 연결되어 있으며, 현재 유일한 장기 보유 지표 원천이다.
- **Amplitude**: 최근 도입되었으며, 무료 플랜을 사용 중이다.
- **Sentry**: 최근 연결되었으며, 무료 플랜을 사용 중이다.
- 현 시점은 **GA4 단독 → Amplitude 중심**으로 이동하는 과도기이다.
- 1차 구현은 ADR 001에 따라 **Amplitude-first**로 진행하며, GA4 연동 코드는 작성하지 않는다.
- Sentry는 에러 분석 확장 단계에서 별도 `ErrorSourceAdapter`로 추가한다.
- 동일 개념이라도 원천별로 정의·집계 방식이 완전히 일치하지 않을 수 있으며, 원천이 다른 값을 단순 비교하지 않도록 주의해야 한다.

#### 1.4.2 외부 서비스 플랜 제약

- Amplitude 무료 플랜과 Sentry 무료 플랜의 한도(이벤트 수, 에러 수, API 호출량, 데이터 보관 기간 등) 범위 내에서 동작해야 한다.
- 특히 Sentry 무료 플랜은 이벤트 보관 기간이 짧으므로, 장기 비교가 필요한 지표는 시스템이 자체 스냅샷으로 보존해야 한다.

#### 1.4.3 AI 사용 전제

- 팀은 현재 ChatGPT Plus, Claude Pro, Gemini Pro 등 **웹·데스크톱 구독형 상품**을 보유하고 있다.
- 본 구독 상품들은 공식적으로 프로그래밍 방식의 API 자동화에 사용할 수 없다. 따라서 자동 호출이 필요한 경로에는 **별도의 API 키(유료 API 또는 각 제공자의 무료/저가 API 티어)** 가 필요하다.
- 구체적인 AI 제공자·모델·키 조달 방식은 13장 오픈 이슈로 관리한다.

#### 1.4.4 예산 전제

- Amplitude, Sentry는 **무료 플랜 한도 내에서 운영**해야 한다. 한도 초과가 예상되면 플랜 업그레이드 여부는 별도 승인 사안으로 다룬다.
- AI 호출료와 서버 운영비는 **가성비 수준의 유료 지출이 허용**된다. 단, 비용은 모니터링 가능해야 하며 예산 한도를 초과하지 않도록 통제되어야 한다.
- 자동화 경로의 AI 호출은 유료 API(저가 모델 포함) 또는 무료 티어 API를 기본 선택지로 삼고, 구독형 상품(Plus/Pro)을 자동화에 우회 사용하지 않는다.

## 2. 용어 정의

### 2.1 지표(Metric)

서비스 상태를 판단하기 위해 수집하는 수치 데이터.  
예: 활성 사용자 수, 회원가입 완료율, 결제 전환율, 핵심 기능 이용률

### 2.2 스냅샷(Snapshot)

특정 시점 또는 특정 기간 기준으로 조회한 지표 값

### 2.3 리포트(Report)

지표 현황, 이전 기간 대비 변화, 해석, 권장 액션 등을 정리한 결과물

### 2.4 경고(Alert)

사전에 정의한 기준을 넘는 이상 변화가 발생했을 때 즉시 전달되는 알림

### 2.5 분석 대상 기간

리포트를 생성하기 위해 사용하는 기준 기간  
예: 이번 주, 지난주, 이번 달, 지난달

### 2.6 전달 채널

리포트와 경고를 팀에 공유하기 위한 메시지 채널  
예: Discord 등 협업 채널

### 2.7 에러 이벤트(Error Event)

오류 모니터링 도구에서 수집한 예외 또는 장애 정보  
예: 특정 화면에서 발생한 JavaScript 에러, API 요청 실패, 서버 예외

### 2.8 이슈 그룹(Issue Group)

동일하거나 유사한 에러를 하나의 문제 단위로 묶은 그룹

### 2.9 영향 구간

에러가 주로 발생한 화면, 기능, API, 사용자 흐름, 릴리즈 버전 등의 맥락 정보

### 2.10 기준 타임존

리포트의 날짜·시간 경계를 판단하기 위한 기준. 본 기능은 **Asia/Seoul (UTC+9)** 을 기본 기준으로 한다.

### 2.11 주차 경계

주간 리포트의 "한 주"는 **월요일 00:00:00 ~ 일요일 23:59:59 (Asia/Seoul)** 을 기준으로 한다.

### 2.12 월 경계

월간 리포트의 "한 달"은 **해당 월 1일 00:00:00 ~ 말일 23:59:59 (Asia/Seoul)** 을 기준으로 한다.

### 2.13 민감정보

에러 메시지, 스택 트레이스, 요청 본문 등에 포함될 수 있는 개인식별정보(이메일, 전화번호, IP 등), 인증 정보(토큰, 키, 쿠키), 재무 정보(카드번호 등). 외부 시스템(Discord, AI 제공자)으로 전송되기 전에 마스킹 대상이 되는 값.

### 2.14 멱등성 키

"같은 의미의 리포트"를 식별하기 위한 키. 리포트 유형, 대상 기간, 리포트 버전 등을 조합해 생성하며 중복 전송 방지에 사용한다.

## 3. 이해관계자

### 3.1 주요 사용자

- 서비스 운영자
- 제품 기획자
- 개발자
- 데이터 분석 담당자

### 3.2 사용자 목표

- 핵심 지표를 대시보드에 직접 접속하지 않고도 확인하고 싶다.
- 단순 수치가 아니라, 이전과 비교했을 때 무엇이 달라졌는지 알고 싶다.
- 이상 변화가 생기면 빠르게 인지하고 싶다.
- AI가 제안하는 원인 가설과 점검 항목, 개선 액션을 참고하고 싶다.
- 동일한 문제에 대해 중복 알림이 반복 발송되지 않기를 원한다.

## 4. 기능 목표

본 기능은 다음 목표를 만족해야 한다.

1. 핵심 지표를 정기적으로 자동 수집할 수 있어야 한다.
2. 지표를 비교 가능한 형식으로 정리할 수 있어야 한다.
3. 기준 기간 대비 증감 및 변화율을 계산할 수 있어야 한다.
4. 이상치 또는 주의가 필요한 변화를 판별할 수 있어야 한다.
5. 오류 모니터링 도구의 에러 정보를 함께 수집할 수 있어야 한다.
6. 에러가 어디에서 발생했는지 화면, 기능, API, 릴리즈 등 맥락으로 파악할 수 있어야 한다.
7. 지표 변화와 에러 발생을 함께 해석할 수 있어야 한다.
8. 수치만 나열하지 않고, 이해하기 쉬운 요약을 제공해야 한다.
9. 개선 방향 및 우선 확인 항목을 제안할 수 있어야 한다.
10. 시스템은 **제한된 도구를 사용하는 AI 분석 시스템**으로 동작해야 하며, AI는 근거 기반의 원인 가설과 액션을 제시할 수 있어야 한다.
11. 팀 커뮤니케이션 채널로 자동 공유할 수 있어야 한다.
12. 이력 저장과 재발송 방지 등 운영 관리를 지원해야 한다.
13. 지표 원천 이동(GA4 → Amplitude, 이후 Sentry 에러 확장) 과도기 동안, 원천별 정의 차이를 감안한 비교가 가능해야 한다.
14. Amplitude/Sentry 무료 플랜의 쿼터·보관 한도를 초과하지 않아야 한다.
15. AI 호출 비용과 서버 운영비는 가성비 예산 한도 내에서 통제 가능해야 한다.
16. 민감정보는 외부 전송 전에 마스킹되어야 한다.
17. 동일 리포트가 재실행·재시도 시에도 중복 전송되지 않아야 한다(멱등성).
18. 시스템 자체의 실행 상태(성공/실패/지연)를 관측할 수 있어야 한다.

## 5. 사용자 시나리오

### 5.1 주간 리포트 확인

- 시스템은 매주 정해진 시각에 핵심 지표를 조회한다.
- 시스템은 전주 대비 변화율을 계산한다.
- 시스템은 요약 리포트를 생성하여 팀 채널에 전송한다.
- 사용자는 채널에서 주요 지표 현황과 변화, 권장 액션을 확인한다.

### 5.2 월간 리포트 확인

- 시스템은 매월 정해진 시각에 월간 지표를 집계한다.
- 시스템은 이번 달과 지난달을 비교한다.
- 시스템은 가장 크게 변한 지표와 월간 추세를 요약하여 전송한다.

### 5.3 이상 변화 감지

- 시스템은 일정 주기로 지표를 확인한다.
- 특정 지표가 기준치 이상 하락하거나 상승하면 경고를 생성한다.
- 시스템은 중복 여부를 확인한 뒤, 새로운 경고만 전달 채널에 전송한다.

### 5.4 에러 이상 징후 확인

- 시스템은 일정 주기로 오류 모니터링 도구의 에러 정보를 조회한다.
- 시스템은 새롭게 증가한 에러, 반복적으로 발생하는 에러, 특정 릴리즈 이후 증가한 에러를 식별할 수 있어야 한다.
- 시스템은 에러가 주로 발생한 화면, 기능, API, 사용자 흐름, 릴리즈 버전을 함께 요약할 수 있어야 한다.
- 시스템은 필요 시 지표 하락과 에러 증가를 함께 묶어 보여줄 수 있어야 한다.

### 5.5 수동 실행

- 운영자는 특정 날짜 또는 특정 리포트 유형에 대해 수동으로 리포트 생성을 실행할 수 있다.
- 시스템은 요청 조건에 맞는 리포트를 생성하고 결과를 반환하거나 전송한다.

### 5.6 실패 확인

- 외부 분석 도구 조회 또는 전송 채널 전송에 실패한 경우 시스템은 실패 이력을 저장한다.
- 운영자는 실패 원인을 확인할 수 있어야 한다.

### 5.7 재실행 및 멱등성

- 운영자가 이미 전송된 리포트와 동일한 (유형 + 대상 기간)으로 수동 재실행을 요청한 경우, 시스템은 기본적으로 **재전송을 건너뛰고** "이미 전송됨" 상태를 반환한다.
- 운영자는 "재전송 허용" 플래그를 명시적으로 지정하여 재전송을 요청할 수 있다.
- 재전송된 메시지는 본문에 재전송 식별 표시(예: `[재전송]`)와 재실행 시각을 포함한다.
- AI 생성 내용 또는 원천 데이터가 달라져 리포트 버전이 증가한 경우, 시스템은 이를 "재전송"이 아닌 신규 버전으로 간주하고 별도 전송한다.

## 6. 기능 요구사항

### 6.1 지표 조회 기능

#### 6.1.1 지표 정의 관리

- 시스템은 추적 대상 지표 목록을 관리할 수 있어야 한다.
- 각 지표는 다음 정보를 포함할 수 있어야 한다.
  - 지표 식별 키
  - 지표 이름
  - 지표 설명
  - 지표 단위(숫자, 퍼센트 등)
  - 좋은 방향(증가가 좋은지, 감소가 좋은지)
  - 경고 기준
  - 활성 여부

#### 6.1.2 외부 분석 도구 조회

- 시스템은 외부 분석 도구에서 각 지표 값을 조회할 수 있어야 한다. 1차 구현의 지표 원천은 Amplitude로 한정한다.
- 시스템은 주간, 월간 등 기간 조건을 지정하여 조회할 수 있어야 한다.
- 시스템은 조회 결과를 내부 표준 형식으로 변환할 수 있어야 한다.
- 시스템은 지표 조회 실패 시 해당 지표에 대한 오류 정보를 기록해야 한다.
- **각 지표는 원천을 명시해야 하며, 원천이 다른 값을 직접 비교하지 않아야 한다.** 1차 구현의 지표 원천 enum은 Amplitude만 포함한다.
- **Amplitude·Sentry 무료 플랜의 API 호출 쿼터와 샘플링 특성을 고려하여, 한 실행 사이클에서 소비되는 호출 수가 예측 가능하도록 관리해야 한다.**

#### 6.1.3 세그먼트 조회

- 시스템은 필요 시 지표를 세그먼트 기준으로 조회할 수 있어야 한다.
- 세그먼트 예시는 다음과 같다.
  - 플랫폼
  - 디바이스 유형
  - 유입 경로
  - 사용자 유형
- 세그먼트별 값은 전체 값과 구분되어 저장될 수 있어야 한다.

#### 6.1.4 과도기 데이터 처리

- GA4와 Amplitude 값을 병행 저장하는 기능은 1차 구현 범위에 포함하지 않는다.
- Amplitude 전환 이전 기간은 대표 값 비교가 아니라 "신규 수집" 또는 "도입 이전"으로 표시한다.
- Amplitude/Sentry 도입 이전 기간을 포함하는 리포트에서는 해당 기간의 데이터 부재를 "도입 이전"으로 명시적으로 표시해야 한다.
- 원천이 변경된 지표에 대해서는 변경 시점을 기록하고, 변경 전후 값을 동일 추세로 표시하지 않아야 한다.

### 6.2 지표 저장 기능

- 시스템은 조회한 지표 값을 스냅샷 형태로 저장할 수 있어야 한다.
- 저장 항목은 최소 다음을 포함해야 한다.
  - 지표 식별 키
  - 대상 기간 또는 기준 일자
  - 실제 값
  - 세그먼트 정보(있는 경우)
  - 원본 응답 또는 추적 가능한 참조값
  - 수집 시각

### 6.3 비교 및 계산 기능

#### 6.3.1 기간 비교

- 시스템은 현재 기간과 이전 기간의 값을 비교할 수 있어야 한다.
- 비교 방식은 최소 다음을 지원해야 한다.
  - 이번 주 vs 지난주
  - 이번 달 vs 지난달
  - 최근 4주 vs 직전 4주

#### 6.3.2 변화율 계산

- 시스템은 현재 값과 이전 값을 기반으로 변화량 및 변화율을 계산할 수 있어야 한다.
- 이전 값이 0이거나 누락된 경우에도 안전하게 처리할 수 있어야 한다.
- 계산 결과는 사용자에게 이해 가능한 형식으로 표현되어야 한다.

### 6.4 이상치 및 경고 판별 기능

#### 6.4.1 규칙 기반 판별

- 시스템은 지표별로 정의된 기준에 따라 이상 여부를 판별할 수 있어야 한다.
- 판별 기준 예시는 다음과 같다.
  - 지난주 대비 20% 이상 하락
  - 지난달 대비 15% 이상 하락
  - 특정 값 이하로 감소
  - 특정 세그먼트에서만 급격한 변화 발생
- **최소 표본 조건**: 기준 기간과 이전 기간 모두에서 최소 표본 수(지표별로 설정 가능, 예: 이벤트 100건 또는 사용자 30명) 이상일 때에만 변화율 기반 판별을 수행한다. 표본이 부족한 경우 "판별 불가"로 표시한다.
- **변화율·절대값 병행**: 작은 값(예: 5 → 2)에서 높은 변화율이 단독으로 경고를 트리거하지 않도록, 변화율 조건과 절대 변화량 조건을 **동시에** 만족할 때에만 경고를 생성한다.
- **비교 기준 부재 시 처리**: 이전 기간에 해당 지표가 수집되지 않은 경우(예: Amplitude 도입 이전)에는 변화율을 계산하지 않고 "신규 수집" 상태로 표시한다.

#### 6.4.2 심각도 분류

- 시스템은 경고를 심각도 수준으로 구분할 수 있어야 한다.
- 심각도 수준은 최소 3단계 이상으로 구분 가능해야 한다.
  - 예: 낮음 / 보통 / 높음

#### 6.4.3 중복 경고 방지

- 동일한 지표와 동일한 원인으로 판단되는 경고는 반복 전송되지 않아야 한다.
- 시스템은 중복 여부를 식별할 수 있는 기준값을 관리해야 한다.

### 6.5 에러 수집 및 분석 기능

#### 6.5.1 에러 조회

- 시스템은 오류 모니터링 도구에서 최근 에러 정보를 조회할 수 있어야 한다.
- 시스템은 최소 다음 정보를 수집할 수 있어야 한다.
  - 에러 식별 정보
  - 발생 시각
  - 에러 메시지 또는 제목
  - 심각도 수준

  - 릴리즈 버전 또는 배포 맥락

#### 6.5.2 에러 그룹화

- 시스템은 동일하거나 유사한 에러를 그룹 단위로 식별할 수 있어야 한다.
- 시스템은 최근 새롭게 등장한 에러와 기존에 반복되던 에러를 구분할 수 있어야 한다.

#### 6.5.3 에러 증가 탐지

- 시스템은 다음과 같은 조건을 기준으로 주의가 필요한 에러를 식별할 수 있어야 한다.
  - 특정 기간 대비 발생 횟수 급증
  - 특정 릴리즈 이후 새롭게 발생
  - 특정 화면 또는 기능에 집중 발생
  - 특정 API 호출에서 반복 발생
  - 특정 사용자군 또는 디바이스에서 집중 발생

#### 6.5.4 문제 위치 요약

- 시스템은 에러가 주로 어디에서 발생했는지를 사람이 이해하기 쉬운 형태로 요약할 수 있어야 한다.
- 위치 정보 예시는 다음과 같다.
  - 특정 화면
  - 특정 사용자 흐름 단계
  - 특정 API 엔드포인트
  - 특정 파일 또는 함수
  - 특정 릴리즈 버전

#### 6.5.5 수정 가이드 보조

- 시스템은 수집한 에러 맥락을 바탕으로 우선 점검이 필요한 후보를 제안할 수 있어야 한다.
- 제안 내용은 최소 다음 범주를 포함할 수 있어야 한다.
  - 점검이 필요한 화면 또는 기능
  - 확인이 필요한 API 또는 서버 응답
  - 검토가 필요한 최근 변경사항 또는 배포 범위
  - 방어 로직, 예외 처리, 입력 검증 보완 필요 여부
- 시스템은 실제 코드 수정을 자동으로 수행하지 않으며, 수정 우선순위 판단을 돕는 참고 정보를 제공해야 한다.

#### 6.5.6 민감정보 마스킹

- 시스템은 Sentry에서 수집한 에러 데이터를 Discord 또는 AI 제공자로 전달하기 전에 민감정보를 마스킹해야 한다.
- 마스킹 대상 예시: 이메일, 전화번호, 카드번호, 주민등록번호, IP 주소, Authorization 헤더, 쿠키, 요청 본문 내 토큰/비밀 키.
- 마스킹 규칙은 설정 가능해야 하며, 신규 패턴이 발견되면 추가할 수 있어야 한다.
- 마스킹 이전 원본은 내부 저장소에서도 보존 기간을 제한해야 한다.

#### 6.5.7 보관 한계 대응

- Sentry 무료 플랜의 이벤트 보관 한도(현재 약 30일)를 초과하는 기간의 조회는 불가하다. 장기 비교가 필요한 에러 지표는 시스템이 주기적으로 자체 스냅샷을 저장해야 한다.
- 보관 한계에 걸려 조회할 수 없는 기간은 "데이터 없음"으로 명시해야 하며, 추세 그래프에서 공백을 허위로 채우지 않아야 한다.

#### 6.5.8 에러 증가 판정 기준

- 6.5.3의 "급증"은 다음 조건 중 하나를 명시적으로 만족해야 한다.
  - 직전 동일 길이 기간 대비 발생 횟수 2배 이상 **그리고** 절대 발생 횟수 최소 임계 초과
  - 특정 릴리즈 태그 이후 최초 발생(신규 에러)
  - 영향 사용자·세션 수가 일정 임계 초과
- 임계값은 지표·서비스 규모에 맞춰 설정으로 관리할 수 있어야 한다.

### 6.6 AI 기반 요약 및 개선안 생성 기능

#### 6.6.1 입력 구성

- 시스템은 AI에 전달할 입력 정보를 구조화할 수 있어야 한다.
- 시스템은 AI 분석 전에 애플리케이션이 먼저 지표 수집, 변화율 계산, 이상치 후보 추출, 에러 요약 등 **기본 분석 파이프라인**을 수행해야 한다.
- 입력에는 최소 다음 정보가 포함되어야 한다.
  - 서비스 또는 제품 맥락
  - 핵심 지표 목록
  - 현재 값
  - 이전 값
  - 변화율
  - 심각도
  - 세그먼트 정보(있는 경우)

#### 6.6.2 생성 내용

- 시스템은 AI를 통해 다음 내용을 생성할 수 있어야 한다.
  - 핵심 변화 요약
  - 가능한 원인 가설
  - 우선 확인할 항목
  - 실행 가능한 개선 액션

#### 6.6.3 출력 제한

- 생성 결과는 **Discord 메시지 한도**(본문 2000자, Embed description 4096자, Embed 합계 6000자)를 초과하지 않아야 하며, 초과 시 사전에 절삭되어야 한다.
- 생성 결과는 수치 근거 없이 단정적인 표현을 피해야 한다.
- 생성 결과가 실패하거나 품질이 낮을 경우, 시스템은 기본 템플릿 기반 메시지로 대체해야 한다.
- 시스템은 AI 생성 결과를 정해진 스키마(JSON 또는 섹션 구분 텍스트)로 요구하고, 스키마 위반 시 재시도 또는 템플릿 대체로 전환해야 한다.

#### 6.6.4 입력 보호 및 프롬프트 가드레일

- AI에 전달하는 입력은 6.5.6 규칙에 따라 민감정보가 제거된 상태여야 한다.
- AI 분석은 **완전 자율형 agent**가 아니라 **제한형 분석 패턴(Bounded tool calling)** 으로 구현해야 한다.
- AI가 사용할 수 있는 도구는 애플리케이션이 제공하는 **소수의 허용된 읽기 전용 도구**로 제한되어야 하며, 원천 시스템을 임의 탐색하거나 쓰기 작업을 수행해서는 안 된다.
- 한 리포트 사이클에서 AI가 수행할 수 있는 tool 호출 수는 상한이 있어야 하며, 상한 초과 시 추가 호출 대신 템플릿 요약 또는 현재 근거만으로 종료해야 한다.
- 시스템은 에러 메시지·본문에 포함될 수 있는 지시 문구(프롬프트 인젝션 후보)가 시스템 프롬프트를 덮어쓰지 않도록 입력을 구획화(예: 지표·에러 영역을 구분 마커로 감싸기)해야 한다.
- 시스템은 AI 생성 결과를 운영자 검토 없이 실제 코드·인프라 변경에 연결하지 않아야 한다.

#### 6.6.5 비용·쿼터 관리

- AI 호출 1회당 입력·출력 토큰 상한을 지정할 수 있어야 한다.
- 한 리포트 사이클에서 소비되는 호출 수와 토큰 합계를 집계하고, 예산 한도 초과 시 추가 호출을 차단하거나 템플릿 요약으로 전환해야 한다.
- 팀이 보유한 ChatGPT Plus·Claude Pro·Gemini Pro 등의 **구독형 상품은 자동 호출에 사용할 수 없음**을 전제로, 자동 호출용 API 키는 별도로 조달·관리해야 한다(1.4.3, 1.4.4 참조).

- 시스템은 생성된 리포트 또는 경고를 협업 채널(Discord)로 자동 전송할 수 있어야 한다.
- 메시지는 사람이 빠르게 읽을 수 있는 형태로 구성되어야 한다.
- 메시지는 제목, 핵심 수치, 요약, 액션 항목을 구분해서 보여줄 수 있어야 한다.
- 메시지 길이는 Discord 한도(6.6.3)를 초과하지 않아야 하며, 초과 시 본문 축약 또는 스레드·첨부 파일로 분리해야 한다.

#### 6.8.2 채널 분리

- 시스템은 리포트 유형에 따라 서로 다른 채널 또는 스레드로 전송할 수 있어야 한다.
  - 예: 주간/월간 리포트 채널, 장애/경고 채널, 시스템 운영 경고 채널

#### 6.8.3 전송 실패 처리

- 메시지 전송 실패 시 **최대 3회**, **지수 백오프(5초 → 15초 → 45초)** 로 재시도해야 한다.
- 최종 실패 시 실패 이력을 저장하고, 시스템 운영 경고 채널에 통지해야 한다.
- 재시도 중에도 멱등성 키(6.11)를 유지해 동일 리포트의 이중 전송을 방지해야 한다.

### 6.9 수동 실행 및 조회 기능

- 운영자는 수동으로 주간/월간 리포트를 생성할 수 있어야 한다.
- 운영자는 특정 날짜를 기준으로 리포트를 다시 생성할 수 있어야 한다.
- 운영자는 과거에 생성된 리포트 이력을 조회할 수 있어야 한다.
- 운영자는 경고 발송 이력을 조회할 수 있어야 한다.

### 6.10 운영 로그 및 이력 관리 기능

- 시스템은 다음 정보를 기록할 수 있어야 한다.
  - 외부 지표 조회 성공/실패 여부
  - 리포트 생성 성공/실패 여부
  - 전달 채널 전송 성공/실패 여부
  - AI 생성 성공/실패 여부
- 운영자는 실패 원인을 추적할 수 있어야 한다.

### 6.11 멱등성 및 재실행

- 시스템은 각 리포트·경고에 대해 (리포트 유형 + 대상 기간 + 리포트 버전)을 조합한 **멱등성 키**를 생성해야 한다.
- 동일 멱등성 키로 이미 전송된 리포트는 중복 전송되지 않아야 한다.
- 수동 재실행은 기본적으로 "이미 전송된 리포트는 건너뛴다"로 동작하며, 운영자가 명시적으로 "재전송 허용" 플래그를 지정한 경우에만 재전송된다.
- 재전송된 메시지는 재전송임을 식별할 수 있는 표시(예: `[재전송]`)를 포함해야 한다.

### 6.12 시스템 자체 관측성

- 시스템은 자체 실행 상태를 다음 항목으로 노출할 수 있어야 한다.
  - 리포트 유형별 마지막 성공 실행 시각
  - 최근 N회 실행의 성공률
  - 외부 도구별(Amplitude, Discord, AI, 이후 Sentry) 호출 실패율
  - AI 호출 실패율 및 사이클별 소비 토큰·비용 집계
  - Amplitude/Sentry 무료 플랜 쿼터 사용량(조회 가능한 범위)
- 예정된 실행이 정의된 시간 이상 지연되거나 누락되면 **시스템 운영 경고 채널**로 별도 알림을 보낼 수 있어야 한다.
- 시스템 운영 경고 채널은 리포트 전달 채널과 분리될 수 있어야 한다.

## 7. 비기능 요구사항

### 7.1 신뢰성

- 일부 지표 조회 실패가 전체 리포트 실패로 이어지지 않아야 한다.
- 일부 에러 조회 실패가 전체 리포트 실패로 이어지지 않아야 한다.
- AI 생성 실패 시에도 최소한의 숫자 기반 요약은 제공되어야 한다.
- 메시지 중복 발송을 최소화해야 한다.

### 7.2 성능

- 주간/월간 리포트는 정해진 실행 주기 내에 생성 완료되어야 한다.
- 지표 수가 증가하더라도 처리 시간이 급격히 증가하지 않도록 고려해야 한다.

### 7.3 확장성

- 초기에는 소수의 핵심 지표만 지원하더라도, 추후 지표 추가가 쉬워야 한다.
- 추후 다른 분석 도구, 오류 모니터링 도구, 다른 전달 채널이 추가될 수 있어야 한다.
- 세그먼트 기준과 리포트 유형이 확장 가능해야 한다.

### 7.4 유지보수성

- 지표 정의, 경고 기준, 리포트 템플릿은 코드 수정 없이 관리할 수 있는 방향을 고려해야 한다.
- 외부 도구 연동 영역과 내부 분석 로직은 분리되어야 한다.

### 7.5 보안

- 외부 분석 도구 인증 정보와 채널 전송용 비밀값은 안전하게 관리되어야 한다.
- 운영용 수동 실행 기능은 권한이 있는 사용자만 사용할 수 있어야 한다.

### 7.6 가시성

- 리포트 생성 및 전송 흐름은 운영자가 확인할 수 있어야 한다.
- 실패 원인과 최근 실행 상태를 확인할 수 있는 수단이 필요하다.

### 7.7 시간·경계 일관성

- 모든 날짜·시간 계산은 기준 타임존(2.10)을 따라야 하며, 서버 타임존·서머타임·배포 환경 변경의 영향을 받지 않아야 한다.
- 주차 및 월 경계는 2.11, 2.12 정의를 따른다.

### 7.8 민감정보 보호

- 외부(Discord·AI 제공자)로 전송되는 데이터는 6.5.6 규칙에 따라 마스킹되어야 한다.
- 내부 저장소에 보존되는 원본 데이터도 보존 기간을 제한하고 접근 권한을 통제해야 한다.

### 7.9 비용·쿼터

- Amplitude/Sentry 무료 플랜의 이벤트·에러·API 호출 한도를 초과하지 않아야 한다. 한도 사용률을 관측 가능한 형태로 노출해야 한다.
- AI 호출은 사이클당 토큰·호출 수·추정 비용 한도를 초과하지 않아야 하며, 한도 근접 시 시스템 운영 경고 채널로 알림을 보내야 한다.
- 서버 운영비는 가성비 범위 내에서 유지되도록 스케일·배치 주기를 설계해야 한다.

## 8. 데이터 요구사항

### 8.1 관리 대상 데이터

시스템은 최소 다음 데이터를 관리해야 한다.

- 지표 정의 정보
- 지표 스냅샷
- 에러 이벤트 또는 에러 그룹 요약 정보
- 리포트 생성 이력
- 경고 발송 이력
- 실행 로그

### 8.2 보관 요구사항

- 과거 지표와 리포트를 비교할 수 있도록 일정 기간 이상 이력을 보관해야 한다.
- 운영 비용과 활용 목적을 고려해 데이터 유형별 보관 기간 정책을 정의할 수 있어야 한다. 초기 권장 값은 다음과 같다(운영 중 조정 가능).
  - 지표 스냅샷: 최소 24개월 (월간 추세 비교)
  - 리포트·경고 이력: 최소 12개월
  - 에러 그룹 스냅샷: 최소 6개월 (Sentry 무료 플랜 30일 한도 보완)
  - 실행 로그 및 AI 호출 로그: 최소 3개월
  - 마스킹 전 원본 에러 상세: 필요 최소 범위로 보관, **14일 이내 자동 파기**

## 9. 권한 및 운영 요구사항

### 9.1 사용자 권한

- 일반 사용자는 전달 채널에서 리포트 내용을 확인할 수 있어야 한다.
- 운영자는 수동 실행, 재전송, 설정 변경 등의 관리 기능을 사용할 수 있어야 한다.

### 9.2 설정 관리

- 운영자는 다음 설정을 관리할 수 있어야 한다.
  - 활성 지표 목록 및 각 지표의 원천(1차: Amplitude, 이후 Sentry 에러 원천 확장)
  - 리포트 스케줄 및 **기준 타임존**
  - 경고 임계치, 최소 표본 수, 변화율+절대값 동시 조건
  - 에러 급증 판정 계수 (배수, 최소 임계)
  - 리포트 수신 채널 및 **시스템 운영 경고 채널**
  - AI 생성 사용 여부, AI 제공자·모델, **사이클당 토큰·호출·비용 상한**, 예산 초과 시 동작(차단 vs 템플릿 전환)
  - **민감정보 마스킹 규칙 세트**(기본 세트 + 서비스별 추가 패턴)
  - **멱등성 키 구성 요소 및 리포트 버전 정책**
  - 전송 실패 재시도 횟수 및 백오프 간격
  - 데이터 유형별 보관 기간

## 10. 예외 및 오류 처리 요구사항

### 10.1 지표 조회 실패

- 특정 지표 조회 실패 시 전체 프로세스는 가능한 범위 내에서 계속 진행되어야 한다.
- 실패한 지표는 리포트에 누락 또는 조회 실패 상태로 표시할 수 있어야 한다.

### 10.2 에러 조회 실패

- 특정 에러 데이터 조회 실패 시 전체 프로세스는 가능한 범위 내에서 계속 진행되어야 한다.
- 실패한 에러 조회 항목은 리포트에 누락 또는 조회 실패 상태로 표시할 수 있어야 한다.

### 10.3 AI 생성 실패

- AI 생성 실패 시 기본 규칙 기반 요약 문구를 사용해야 한다.
- AI 실패 자체가 리포트 전송 실패로 이어지지 않아야 한다.

### 10.4 전달 채널 전송 실패

- 전송 실패 시 **최대 3회**, **지수 백오프(5초 → 15초 → 45초)** 로 재시도해야 한다.
- 최종 실패 시 실패 상태를 기록하고, 시스템 운영 경고 채널에 통지해야 한다.
- 동일 리포트가 중복 전송되지 않도록 멱등성 키(6.11)로 상태를 관리해야 한다.

### 10.5 데이터 이상값

- 값이 비어 있거나 비정상적인 경우 안전하게 처리되어야 한다.
- 계산 불가능한 경우 이를 명시적으로 표시할 수 있어야 한다.

## 11. 우선순위

### 11.1 1차 구현 범위(MVP)

> **범위 결정 근거**: 1차 구현은 Amplitude-first 전략을 채택한다. GA4 연동은 Amplitude 전환 후 폐기될 코드이므로 작성하지 않는다. Sentry 연동과 AI 요약 계층은 Walking Skeleton 검증 이후 2차에서 추가한다. 자세한 결정 배경은 [ADR 001](./adr/001-amplitude-first.md)을 참조한다.

MVP는 다음 항목을 **모두** 포함한다.

#### 11.1.1 핵심 파이프라인

- 핵심 지표 목록 관리 (원천: Amplitude)
- 지표 주기적 조회 (Amplitude 기반, 무료 플랜 쿼터 내)
- 지표 스냅샷 저장
- 전주 또는 전월 대비 비교 ("신규 수집" 및 "판별 불가" 처리 포함)
- 규칙 기반 이상치 판별 (최소 표본 + 변화율·절대값 병행)
- 주간 리포트 생성
- 월간 리포트 생성
- 지표 이상치 경고 메시지 생성
- 전달 채널(Discord) 자동 전송
- 리포트 및 경고 이력 저장
- AI 요약 계층 placeholder 구조 확보 (1차에서는 비활성화, 템플릿 요약으로 대체)

#### 11.1.2 MVP 필수 안전장치

운영 리스크 방지를 위해 다음 항목은 MVP 범위에 포함한다.

- **멱등성 키 기반 중복 전송 방지**: 스케줄·재시도·수동 재실행에 공통 적용
- **기본 자체 관측성**: 리포트 유형별 마지막 성공 실행 시각, 직전 실행 성공/실패 상태
- **민감정보 마스킹 구조 준비**: 2차(Sentry)·AI 연동 이전에 마스킹 계층을 적용할 수 있도록 확장 가능한 구조만 확보

### 11.2 2차 확장 범위

- **Sentry 에러 조회**: 에러 그룹 정보 수집, 발생 위치 요약
- **에러 경고 메시지**: 심각한 에러에 대한 별도 경고 채널 전송
- **AI 요약 계층 활성화**: bounded tool calling 기반 요약 및 액션 제안, AI 사용량 로그
- **지표 + 에러 결합 리포트**: 지표 하락과 에러 증가를 함께 해석
- **민감정보 마스킹 완성**: Sentry 데이터 및 AI 제공자 전송 이전 적용
- 세그먼트별 상세 분석 강화
- 주간 리포트 고도화
- 수동 재실행 관리자 UI
- 여러 전달 채널 지원
- 최근 배포 이력, 오류 로그 등 외부 맥락 데이터 연계
- 자체 관측성 확대: 도구별 실패율 추세, 쿼터 사용률 대시보드, 실행 지연 자동 감지·알림, AI 호출 비용 누적치
- 에러-지표 상관 분석 (지표 하락 + 에러 증가 시점 매칭)
- AI 모델 라우팅 (저비용 기본, 장문 분석 시 고급 모델)

## 12. 수용 기준

다음 조건을 **측정 가능한 형태로** 만족하면 1차 구현이 완료된 것으로 본다.

1. 사전에 정의한 핵심 지표 N개(N은 설정 값)를 정해진 스케줄(기본: 매주 월요일 09:00 KST, 매월 1일 09:00 KST)에 자동 조회하며, **최근 4회 주간 사이클 기준 조회 성공률 ≥ 95%** 를 만족한다.
2. ~~Sentry로부터 에러 그룹 정보를 자동으로 조회하며, 각 리포트 대상 기간에 대해 주요 발생 위치(화면·API·릴리즈 버전 중 하나 이상)를 요약 필드로 포함한다.~~ → **2차 수용 기준으로 이동** (Sentry 연동은 11.2 범위)
3. 기준 기간 대비 변화율을 계산하며, 최소 표본 조건(6.4.1) 미만인 지표는 "판별 불가"로 명시한다. 이전 기간 데이터가 없는 경우 "신규 수집"으로 표기한다.
4. 이상 변화가 있는 **지표**를 규칙 기반으로 판별하고, 심각도(낮음/보통/높음)를 부여한다.
5. 주간 및 월간 리포트를 생성하여 지정된 Discord 채널로 자동 전송하며, 전송 메시지는 Discord 한도 이내(6.6.3)로 포맷된다.
6. 경고 조건을 만족하는 경우, 주간/월간 리포트와 분리된 경고 채널로 경고 메시지를 별도 전송할 수 있다.
7. AI를 사용하지 않아도 템플릿 기반 요약으로 리포트 전송이 성공한다. AI 비활성화 상태는 실행 로그에 기록된다.
8. 운영자는 직전 90일 이상의 리포트·경고 전송 이력과 성공/실패 상태를 조회할 수 있다.
9. 동일 멱등성 키(6.11)를 갖는 리포트·경고는 재실행 시에도 중복 전송되지 않는다. 재전송은 운영자 플래그에 의해서만 이루어진다.
10. Discord로 전송되는 데이터에 민감정보 마스킹 확장 구조가 준비되어 있다. (AI 제공자 전송 마스킹 적용은 2차)
11. 시스템은 리포트 유형별 마지막 성공 실행 시각과 최근 성공률을 운영자가 확인할 수 있는 형태로 제공한다.
12. Amplitude 무료 플랜 API 호출 수가 실행 로그에서 추적 가능하다.
